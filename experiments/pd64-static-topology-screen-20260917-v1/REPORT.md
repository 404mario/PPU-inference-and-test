# DeepSeek-V4.1-Flash：64 卡 P/D 拓扑筛选与服务 profile

四套 STATIC DSpark 拓扑已经完成阶段筛选。当前领先候选是 **2P8+6D8**：在 1.4 请求/秒的提供负载下，精确正确完成速率为 **0.672 请求/秒**，TTFT p95 为 46.34 秒，TPOT p95 为 34.83 毫秒。该结果用于确定下一轮实验方向，尚未达到生产验收标准。

P（prefill）负责输入处理；D（decode）负责逐 token 生成；EP（专家并行）表示一个模型实例的专家分布范围。模型为 DeepSeek-V4.1-Flash，硬件为 8 节点、64 张 ZW-M890P。四套方案使用 attention TP=1 和原生 STATIC DSpark，冻结相同的 2k/8k/28k 合成精确任务。

## 拓扑结果

下表是精确答案正确、传输完整且 usage 有效的完成请求/秒，分母包含停止发请求后的排空时间。

| 拓扑 | 0.5 req/s | 0.8 req/s | 1.0 req/s | 1.2 req/s | 1.4 req/s |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2P8+6D8 | 0.406 | 0.534 | 0.604 | 0.644 | **0.672** |
| 2P8+3D16 | 0.404 | 0.547 | 0.597 | 未完整 | 未测 |
| 4P8+4D8 | 0.410 | 0.569 | 0.579 | 0.610 | 0.564 |
| 4P8+2D16 | 0.402 | 0.532 | 0.583 | 0.612 | 0.514 |

2P8+3D16 的 1.2 档完成了 120 次传输，其中 119 次精确正确，但该恢复阶段未完整结束，因此没有把该点写入主表。4P8+4D8 的 1.0 档同样为 119/120，其余已完成正式档均精确正确。

在 1.4 请求/秒下，4P8+4D8 和 4P8+2D16 的正确完成速率分别比 2P8+6D8 低 16.1% 和 23.5%。两者 TTFT p95 分别为 60.48 秒、76.27 秒。增加 P 卡同时减少 D 实例，没有形成净收益。

## profile 结论

四套拓扑的 DSpark 接受率约为 79%，平均接受长度约 4.95 token。EP16 没有提升草稿质量，但 TPOT 普遍增加约 8%–24%，说明跨节点专家通信在当前负载下主要形成额外 decode 成本。

实际 KV 缓存传输平均约 0.18–0.58 秒，不是几十秒 TTFT 的主体。以 2P8+6D8 为例，到达率从 0.5 增至 1.4 请求/秒时：

| 指标 | 0.5 req/s | 1.4 req/s |
| --- | ---: | ---: |
| P forward 均值 | 6.60 s | 7.99 s |
| P bootstrap 均值 | 0.06 s | 4.18 s |
| KV 传输均值 | 0.31 s | 0.47 s |
| D 状态可用阶段均值 | 6.81 s | 11.33 s |
| P 等待队列最大值 | 0 | 4 |

`D 状态可用阶段` 包含等待 P 完成和交接就绪，不能解释为纯 DMA。当前长尾主要由 P 前向、分块调度、bootstrap 和跨阶段就绪等待累计形成。

此前 P32/D32 在 C48 预热下出现 KV 超时；将门禁改为 C8 后没有再次出现，说明旧失败主要受瞬时并发压力影响，不能表述为四个 P 实例必然失败。4P8+4D8 的低负载 TTFT 仍有明显漂移，低负载单点不用于稳态裁决。

## 下一轮实验

第一项补测 **3P8+5D8（P24/D40、EP8）**，只运行 1.0、1.2、1.4 请求/秒。这个点能判断增加一个 P8 实例是否足以抵消少一个 D8 实例。若它的 1.4 档正确完成速率至少达到 2P8+6D8 的 98%，且 TTFT p95 改善至少 10%，再进入重复验证；否则保留 2P8+6D8。

第二项在 **2P8+6D8** 上运行匹配普通解码，保持拓扑、模型精度、请求序列、网关策略和缓存预算不变，只删除 DSpark 参数。该对照用于量化 STATIC DSpark 在 P/D 服务中的净收益，并冻结后续 SLO（服务延迟目标）门槛。

第三项在预热后，只对一个 P8 和一个 D8 实例采集固定步数的短窗口算子 profile，分析注意力、MoE、通信和主机调度占比。profile 不计入主性能数字，也不能把算子占比直接当作可实现的端到端加速。
